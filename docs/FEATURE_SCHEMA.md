# Participant Feature-Table Schema

The reconstructed modeling workflow consumes participant-level feature
CSV files.

## Required historical structure

The historical standalone modeling code selects:

```python
features_df.iloc[:, 1:-1]
```

Therefore column position matters in the historical-compatible workflow.

The expected layout is:

1. participant identifier;
2. one or more numerical feature columns;
3. `ADHD` label as the final column.

For the five-stage historical analysis, the standard form is:

```text
Patient_ID
Sleep_ID_1
Sleep_ID_2
Sleep_ID_3
Sleep_ID_4
Sleep_ID_5
ADHD
```

## Column definitions

### `Patient_ID`

Participant identifier used to distinguish participant-level rows.

The public synthetic example uses identifiers such as:

`SYN001`

These identifiers are artificial.

### `Sleep_ID_1` through `Sleep_ID_5`

Numerical graph-derived features generated by the historical
feature-extraction workflow.

Historical presentation names are:

- `Sleep_ID_1` → Wake
- `Sleep_ID_2` → Sleep Stage 1
- `Sleep_ID_3` → Sleep Stage 2
- `Sleep_ID_4` → Sleep Stage 3-4
- `Sleep_ID_5` → Rapid Eye Movement

The public synthetic values do not represent real graph measurements.

### `ADHD`

Historical label column.

The historical modeling implementation converts:

```python
features_df["ADHD"] == "Y"
```

to binary integer labels.

Thus:

- `Y` becomes `1`;
- all other values become `0`.

For legitimate use with research data, label encoding should be checked
against the applicable data dictionary before analysis.

## Public versus protected data

The repository may contain artificial example feature tables.

It must not contain unauthorized:

- raw PSG recordings;
- participant-identifying metadata;
- protected clinical records;
- participant-derived screenshots;
- locally exported clinical feature tables.

The synthetic files under `examples/` exist specifically to demonstrate
the interface without crossing this data boundary.
